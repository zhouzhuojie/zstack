# Zstack

A localization of Poteto's pstack (reproduce first, smallest change, prove
it works, cross-family review) for any harness and any repo. The
discipline lives here; the project specifics live in a small adapter
file; the enforcement stays in the project's own gate (test script,
`make`, CI). The stack's contribution is the workflow; the project
contributes the truth.

## Step 0 — adapter

Before any task, resolve the project adapter:

1. `.zstack/project.md` at the repo root.
2. `~/.zstack/adapters/<basename>.md`, basename from the origin remote
   URL with `.git` stripped, else the repo root dir name.
3. Neither → draft one from the repo's own instructions
   (AGENTS.md / CLAUDE.md / CONTRIBUTING / CI config), show the draft
   labeled "draft, unverified", and offer to save it. Never invent a
   gate command silently; a draft gate that has not been run is a guess.

The adapter names: `gate` (the only verification command(s)), `groups`
(what-change → what-to-run: an inline table, or a pointer to the doc of
record — a pointer keeps one truth), `broad gate` (the after-any-change
gate), `release gate` (the full/CI tier, run only when asked), `probes`
(one-off measurement commands and their limits), `truth` (truth order),
`ticket` (work order format and where it lives; the adapter owns the
format), `boundary` (data-vs-code rule), `strings` (user-facing string
pipeline), `machines` (state machines of record), `measurements`
(the measured-comparison rules the `tuning` playbook honors),
`registries` (what you must register in before adding: regions, slots,
cards), `language` (language policy), `branch` (worktree and branch
rules), `docs` (read-first list).

`gate` is required. Without `groups`, run the `broad gate` and say the
group table is missing — never guess a group silently. No adapter → no
work beyond the draft.

## Install scope

Skills install user-global at `~/.agents/skills/` (this stack's
default); harnesses that read the agentskills.io layout also accept
project-local `.agents/skills/` in a repo. Verify skills generated by
`property-test` land project-local, next to the code they guard.

## Non-negotiables

- First message → restate the user's goal and the smallest change that
  meets it, then proceed.
- Ticket before work, per the adapter's `ticket` field. No acceptance
  criteria, no work.
- Truth order per the adapter (default: code > data/config > gate output
  > status docs > other docs). Numbers come from data/config, not from
  docs.
- Data before code, per the adapter's `boundary`. If adding content
  seems to need code, stop and ask whether the system is missing a
  data-driven entry point.
- Verification only through the adapter's gate. Never substitute a
  hand-run test command; never pipe or redirect test output where the
  project forbids it. Probes measure; gates verify.
- One system per change, small commits, each commit ends green.
- The adapter's `groups` table decides which gate a change owes.
- Proceed on reversible work and present the result; the irreversible —
  push, PR, merge, deletion, anything writing outside the repo — waits
  for the user's word. Worktrees and branch policy per the adapter's
  `branch`. When the user says 不要停 / "run until done" / "going to
  bed", keep going through the whole playbook, including the gate.

## Playbooks

Match the task, open the file at `playbooks/<name>.md` (relative to this
skill's folder), and follow its steps in order, saying which step you are
on.

| Task | Playbook |
|---|---|
| A read-only question: how does X work, why, are we sure | `investigation` |
| Something is broken, or the gate is red | `bug-fix` |
| New content: entries, config values, copy — data only | `data-add` |
| Tuning a measured variable: perf, balance, thresholds | `tuning` |
| New or changed behavior in code | `feature` |
| The user wants to SEE a state machine, or a bug as a path through states | `statechart` |
| Tests can't reach a case (race, retry, state corner), or "prove this invariant" | `property-test` |
| Finished work needs landing | `shipping` |

No fit → write the ticket, break the work into units that each end in a
gate group, and proceed the same way. Do not invent a ninth playbook
in-session.

`statechart` and `property-test` run the vendored pstack skills —
`statechart`, `create-formal-verification-skill`,
`maintain-formal-verification-skill`, contained inside this skill at
`vendor/pstack/` (never top-level) — on the local TLA+ toolchain. Setup
and the exact run command: `tla-toolchain.md` in this folder.

## Models

Read `models.md` in this folder: roles, not brand names, and the
review-panel protocol. Fill the roles from your provider's model list
and pin your picks in `~/.zstack/models.md` — the installer seeds it,
zstack reads it at task start. Never switch a role's family unasked.

## Subagents

- Bulk reads (multi-file sweeps, long logs) go to a subagent; summaries
  stay in the main thread.
- Fresh subagent per round: a fix round or retry gets the original brief,
  every later directive, and the prior report — not a continuation of a
  polluted context.
- Independent or large work belongs on a worktree, per the adapter's
  `branch` field; record the baseline commit first.

## Reply style

Short declarative sentences. Lead with what changes for the user. Label
every claim measured / inferred / guess, and paste the gate's PASS lines
as the evidence for "done". Language policy per the adapter. No is an
acceptable answer: decline scope the project's roadmap or docs
explicitly veto.
